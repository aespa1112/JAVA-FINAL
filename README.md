# 基於 Java 與 SQLite 的會計師專業記帳系統
> Professional Bookkeeping & Audit System for Accountants — Java 17 + JavaFX + SQLite（第五版：雙人審核加固與 Schema v3）

| 項目 | 內容 |
|---|---|
| 專案名稱 | 會計師專業記帳與審計軌跡系統 |
| 開發語言 | Java 17 (純 Java SE，不使用 Spring 等框架) |
| 使用者介面 | JavaFX (FXML + CSS) |

## 一、專案定位與研究動機

### 1.1 使用者情境
會計師（記帳士）通常同時為 **10～50 家中小企業客戶** 處理帳務，其工作特性為：

1. **多客戶、獨立帳套**：每個客戶的帳務必須完全隔離，不可混淆。
2. **高度機密性**：客戶財務資料常受保密協議約束，禁止上傳第三方雲端。
3. **行動查帳需求**：需攜帶資料至客戶端或稅捐機關，常在無網路環境作業。
4. **法規合規要求**：憑證須連續編號、已過帳憑證不得任意竄改，須保留完整審計軌跡（Audit Trail）。

### 1.2 為何選擇 SQLite（架構決策，非技術偷懶）

| 需求 | SQLite 的對應優勢 |
|---|---|
| 一個客戶一個帳套 | **一個客戶 = 一個 `.db` 檔案**，天然物理隔離，切換客戶即切換檔案 |
| 資料機密 | 完全本地化、零網路依賴，可放入加密隨身碟；支援 `PRAGMA` 高可靠度參數 |
| 行動查帳 | 免安裝資料庫伺服器，綠色免安裝，隨開即用 |
| 備份與交付 | 支援 `VACUUM INTO` 與 WAL Checkpoint，單一檔案即為完整備份，可直接交付客戶存檔 |
| 讀多寫少 | 會計作業為「少量寫入、大量查詢報表」，完全符合 SQLite 效能特性 |

## 四、資料庫架構與安全機制（13 個觸發器與 Schema v3 遷移）

### 4.1 資料庫表結構

1. **`system_meta`**：儲存系統與帳套元資料（例如 `client_id`），防止將不同客戶的備份檔覆蓋至目前帳套。
2. **`voucher_sequences`**：維護各月份的傳票最新流水序號，以 O(1) 時間複雜度取得下一編號，且草稿刪除後號碼不倒退，絕不重用。
3. **`accounts`**：會計科目主檔，包含代碼、名稱、五大類別、借貸方向、是否末級（`is_leaf`）與啟用狀態（`enabled`）。
4. **`fiscal_periods`**：會計期間檔，以年月（`year`, `month`）唯一索引，狀態為 `OPEN` 或 `CLOSED`。
5. **`vouchers`**：傳票主檔，記錄期間、傳票號、傳票日期、摘要、狀態（`DRAFT`, `POSTED`, `VOID`）、制單人、審核人、沖銷關聯（`reversed_id`）。
6. **`voucher_entries`**：傳票分錄明細，記錄所屬傳票、行號、科目、金額（以 `INTEGER` 存分/cents）、單向借貸約束（`CHECK(NOT (debit_minor > 0 AND credit_minor > 0))`）。
7. **`audit_log`**：不可竄改之審計軌跡日誌，記錄動作、目標表、記錄編號、操作人、舊值、新值與時間。
8. **`vouchers_fts`**：FTS5 虛擬全文檢索表，利用 Trigram 分詞加速傳票摘要與號碼搜尋。

### 4.2 結構遷移與版本管理（`PRAGMA user_version = 3`）

系統內建 `migrateSchema` 機制：
- 透過 `PRAGMA user_version` 判斷資料庫版本，目前版本為 **3**。
- **階梯式升級防護**：
  - `version < 2`：重建所有 13 個 Trigger。
  - `version < 3`：建立 `system_meta` 與 `voucher_sequences` 系統表、重建最新 Trigger、初始化 `client_id`。
- **全事務包覆（Atomic Transaction）**：所有升級操作與 `PRAGMA user_version = 3` 包裹在單一交易內（`conn.setAutoCommit(false)`），杜絕遷移中斷造成資料庫失去防護之風險。

### 4.3 資料庫層 13 個防護觸發器（Trigger）清單

本系統實作了業界罕見的 13 個資料庫層級防護觸發器，形成堅固的不可竄改安全邊界：

| 編號 | Trigger 名稱 | 觸發時機與目標 | 防護安全效益 |
|---|---|---|---|
| 1 | `trg_vouchers_fts_ai` | AFTER INSERT ON vouchers | 自動將新傳票同步寫入 FTS5 全文檢索索引 |
| 2 | `trg_vouchers_fts_ad` | AFTER DELETE ON vouchers | 自動將已刪除草稿自 FTS5 索引中移除 |
| 3 | `trg_vouchers_fts_au` | AFTER UPDATE ON vouchers | 自動更新 FTS5 全文檢索索引內容 |
| 4 | `trg_voucher_no_delete` | BEFORE DELETE ON vouchers | **已過帳憑證（POSTED）禁止刪除**，強制使用紅字沖銷 |
| 5 | `trg_voucher_no_update` | BEFORE UPDATE ON vouchers | **已過帳憑證完全唯讀**，禁止修改任何主檔欄位（防竄改） |
| 6 | `trg_voucher_status_lock` | BEFORE UPDATE OF status ON vouchers | **狀態機單向性保護**：嚴禁由 `POSTED` 或 `VOID` 回退至 `DRAFT` |
| 7 | `trg_voucher_balance_on_post` | BEFORE UPDATE OF status ON vouchers | **過帳瞬間強制借貸平衡**，且至少具備兩筆分錄 |
| 8 | `trg_entry_no_insert_on_posted` | BEFORE INSERT ON voucher_entries | **分錄防護**：非草稿傳票嚴禁追加插入分錄 |
| 9 | `trg_entry_no_update_on_posted` | BEFORE UPDATE ON voucher_entries | **分錄防護**：非草稿傳票嚴禁竄改分錄金額、科目或摘要 |
| 10 | `trg_entry_no_delete_on_posted` | BEFORE DELETE ON voucher_entries | **分錄防護**：非草稿傳票嚴禁刪除任何分錄 |
| 11 | `trg_period_locked` | BEFORE INSERT ON vouchers | **期間鎖定**：已結帳鎖定期間（CLOSED）禁止新增憑證 |
| 12 | `trg_audit_immutable_update` | BEFORE UPDATE ON audit_log | **審計日誌唯讀**：禁止竄改任何歷史審計紀錄 |
| 13 | `trg_audit_immutable_delete` | BEFORE DELETE ON audit_log | **審計日誌唯讀**：禁止刪除任何歷史審計紀錄 |

## 五、核心業務邏輯與內控機制

### 5.1 嚴格使用者角色白名單與標準化（`OperatorRole`）

針對模糊比對與泛用特權名稱之漏洞，本系統採用嚴格的白名單與身分規範化：

- **白名單精準封閉**：僅接受系統指定人員（Amy: MAKER, Bob: CHECKER, David: CHECKER, Charlie: AUDITOR）。
- **徹底移除特權與測試殘留名稱**：不接受 `checker`, `maker`, `auditor`, `bobchecker2` 等泛用字串，任何非法或偽冒名稱（如 `"Amy 審核"`）一律拋出 `BusinessException`。
- **身分字串標準化（`normalize`）**：在 Service 入口處統一將傳入字串規範化為標準名稱（如 `"Bob (會計師/審核人)"` 與 `"bob"` 均轉化為 `"Bob"`），確保主檔與審計軌跡一致性。
- 註：本系統以白名單模擬身分角色，生產環境建議對接 RBAC / 身分驗證系統。

### 5.2 紅字沖銷雙人審核控制（Dual Control / Four-Eyes Principle）

紅字沖銷是會計上最高風險的反轉更正操作，本系統落實嚴格的「雙人審核機制」：

1. **重大更正發起**：紅字沖銷由第一位會計師（如 Bob）發起，草稿制單人保留原提出者（Amy），沖銷發起人與關聯原憑證記錄於審計日誌 `REVERSE_INITIATED`。
2. **禁止發起人自行過帳**：在傳票過帳時，系統自審計日誌比對沖銷發起者，若審核人與沖銷發起人為同一人（例如 Bob 發起沖銷又由 Bob 審核），立即拋出：
   `職責分離原則：紅字沖銷發起人（Bob）不得自行審核過帳該沖銷傳票，必須由第二位會計師審核！`
3. **第二位會計師協同過帳**：UI 角色清單具備第二位會計師 **David (會計師/審核人)**，沖銷傳票必須由 David 審核過帳，落實四眼原則。
4. **GAAP 合規實作**：SQLite 層設有 `debit_minor >= 0` 約束以防誤輸負數，沖銷採**借貸方向對調 + `reversed_id` 關聯註記**，報表端以紅字呈現，餘額精確歸零。

### 5.3 草稿跨月修改編號一致性

- 當記帳員將草稿日期由 11 月修改至 12 月時，系統自動偵測月份跨越。
- 同步將 `period_id` 更新至目標期間，並利用 `voucher_sequences` 自動重新產生目標月份的傳票編號（如 `2026-12-0001`），確保編號與日期嚴格一致。

### 5.4 客戶帳套內存 Client ID 防護（改檔名防禦）

- 每個資料庫的 `system_meta` 表中內建儲存 `client_id`。
- 執行資料庫還原（`restore`）時，系統自動開啟備份檔案讀取內部 `client_id`，並與目標資料庫的 `client_id` 比對。若將客戶 B 的備份檔改名為 `client_A_fake.db` 嘗試還原至客戶 A，將被直接攔截並中止還原。
- 檔名推導採用正則去除尾部時間戳 `_\\d{8}_\\d{6}$`，精確區分 `client_A_1` 與 `client_A_2`，且完美相容 Windows 環境下的 `:memory:` 虛擬連線。
- 還原前自動合併 WAL 並建立帶有時間戳的安全快照（`safety_pre_restore_*.db`），還原失敗時自動無損復原。

### 5.5 傳票取號 O(1) 效能與防重用機制

- 建立專用序號表 `voucher_sequences (prefix, last_seq)`。
- 每次取號直接基於主鍵進行更新，取代過去全表掃描 `audit_log` 的沉重開銷，大幅提昇大量傳票建立時之吞吐量。
- 即使草稿傳票被刪除，序號表的 `last_seq` 亦不倒退，確保傳票流水號永遠單調遞增，絕不重用。

### 5.6 跨年度結轉資產負債表

- 損益表各科目於資產負債表中依年度切分：
  - 當前會計年度以前之累積淨損益自動結轉滾入 **3301 保留盈餘**。
  - 當前會計年度之淨損益獨立列示於 **3302 本期損益**。
- 資產總額與負債及權益總額精確平衡。日期解析若遇非標準格式，提供清楚友善之 `BusinessException` 提示。

## 六、測試計畫與 30 項測試案例

系統採用 JUnit 5 進行全方位自動化驗證，目前涵蓋 30 項測試且全數通過（測試中產生的暫存檔案皆隔離於 `target/test-backups` 並自動清理，不污染 `backup/` 目錄）：

| 編號 | 測試案例名稱 | 測試情境說明 | 預期結果 |
|---|---|---|---|
| **T01** | 借貸平衡正常過帳 | 借方 1000、貸方 1000 正常分錄過帳 | 成功過帳，狀態變更為 POSTED |
| **T02** | 借貸不平衡攔截 | 借方 1000、貸方 900 分錄 | 拋出 BusinessException，資料庫無任何寫入 |
| **T03** | 單筆分錄攔截 | 僅提供單邊借方 1000 分錄 | 攔截：複式簿記至少需兩筆分錄 |
| **T04** | 精度測試 | 浮點運算 0.1 + 0.2 | 整數分(cents)儲存，精確等於 0.30 元 |
| **T05** | 刪除已過帳憑證攔截 | 嘗試 DELETE 狀態為 POSTED 的傳票 | Trigger 阻擋（RAISE ABORT），寫入 DENIED 日誌 |
| **T06** | 修改已過帳憑證攔截 | 嘗試 UPDATE 狀態為 POSTED 的傳票主檔或分錄 | Trigger 阻擋，已過帳傳票完全唯讀 |
| **T07** | 紅字沖銷核心機制 | 沖銷已過帳銷貨傳票並由第二位會計師審核 | 產生對沖傳票，借貸對調，兩張傳票均保留，餘額歸零 |
| **T08** | 已結帳期間新增憑證攔截 | 嘗試將傳票寫入已關帳鎖定之會計期間 | Trigger 阻擋，禁止寫入已結帳期間 |
| **T09** | 交易原子性與回滾 | 傳票過帳流程中途模擬拋出異常 | 傳票主檔、分錄、審計日誌全數 rollback |
| **T10** | 職責分離原則驗證 | 制單人 Amy 嘗試審核自己建立之傳票 | 拋出職責分離異常，禁止制單人審核 |
| **T11** | 備份與無損還原 | 備份目前帳套，模擬人為污染後還原 | 備份通過完整性校驗，還原後資料 100% 一致 |
| **T12** | 停用科目防護 | 傳票分錄指定已停用（enabled=0）科目 | 攔截：已停用科目不得錄入分錄 |
| **T13** | 非末級統制科目防護 | 傳票分錄指定父層非末級科目（is_leaf=0） | 攔截：統制科目不得直接記帳 |
| **T14** | 試算表借貸平衡 | 統計區間內所有已過帳分錄 | 借方總額與貸方總額精確平衡 |
| **T15** | 資產負債表恆等式 | 驗證會計恆等式（資產 = 負債 + 權益） | 報表自動包含本期損益與前期結轉，兩側完全平衡 |
| **T16** | 跨年度結轉損益表歸零 | 跨年度時檢驗損益科目滾入保留盈餘 | 舊年度損益結轉至 3301，新年度損益獨立計算 |
| **T17** | 重複沖銷防護 | 對已沖銷過之同一張傳票再次發起沖銷 | 攔截：不可對同一傳票重複進行紅字沖銷 |
| **T18** | 未過帳草稿跨期調整防護 | 將草稿傳票日期調整至已結帳鎖定期間 | 攔截：禁止將草稿調整至已結帳期間 |

## 八、口試與專案報告重點對應表

| 口試提問點 | 系統對應設計與回答策略 |
|---|---|
| **為何選擇 SQLite 而非 MySQL？** | 以「執業會計師多客戶獨立帳套」業務特性出發。一個客戶一個 `.db` 檔，具備天然物理隔離、離線作業、隨身碟攜帶查帳、無伺服器維護成本之優勢。 |
| **如何保證已過帳憑證絕對不被竄改？** | 雙軌防護：Service 層狀態機校驗 + SQLite 核心 Trigger（`trg_voucher_no_update`、`trg_entry_no_update_on_posted` 等）。即使使用第三方 DB 瀏覽器直接連線修改，亦會被 SQLite 引擎強制 ABORT。 |
| **借貸平衡如何確保 100% 正確？** | 三層校驗：UI 層前端即時試算與反饋 → Service 層 `BigDecimal` 精確借貸比對 → 資料庫 Trigger（`trg_voucher_balance_on_post`）過帳前進行 SUM 聚合驗證。 |
| **金額計算如何避免浮點數誤差？** | 遵循金融系統標準：資料庫以最小貨幣單位（Cents/分，`INTEGER`）儲存，業務運算層採用 `BigDecimal` 並指定 Scale，禁止使用 `double` 或 `float`。 |
| **如何落實會計內控職責分離？** | 嚴格區分 MAKER（制單人 Amy）、CHECKER（審核人 Bob, David）、AUDITOR（查帳員 Charlie）。以嚴格白名單精確映射並統一標準化名稱。紅字沖銷由第一位會計師發起，但強制由第二位會計師審核過帳（禁止發起人自審），落實雙人控制（Dual Control）。 |
| **資料庫備份還原如何防範跨客戶混淆？** | 資料庫內建 `system_meta` 表記錄 `client_id`。備份還原時由獨立連線讀取備份庫與目標庫內存之 `client_id`，正則去除時間戳，杜絕改檔名跨帳套覆蓋漏洞。 |
